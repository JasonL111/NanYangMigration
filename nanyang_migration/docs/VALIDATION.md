## 根因与执行链

RC1 的用户截图显示：832 个来源 POP，来源人口 337,827,747，各区有效实际州 5 / 32 / 3 / 13 / 7 / 12，同时本次调用与请求量为零。这把问题缩小到来源和目的地枚举之后、第一次原生移动之前。截图没有单步引擎日志，无法证明是哪个条件或绑定最先挡住请求。RC2 用原生 State/POP 枚举、生成器写出的固定调用及按存在性判断的停止标记，替换此阶段的临时列表、列表参数和布尔值比较。再检查每笔额度和来源标记，避免迭代期间状态改变造成并行抽取或重复迁移。

RC2 的后续实机截图将问题进一步缩小到来源筛选。18 个文化×地区格均启动，225 个目的州份获得正额度，但配对与调用均为零。RC3 从本国实际州进入 POP 迭代，匹配写在脚本里的四种原生文化 ID。尚未接收该文化的来源州无需读到 POP 标记。已接收该文化的来源州只允许来源标记有效的原 POP 使用剩余预算。移人前在目的州写入并回读该文化的接收标记。未能回读时不调用迁移。

在同一组合成人口上注入「POP 变量未写入」条件，原 RC2 ZIP 复现 832、18、225、0 配对、0 调用。RC3 在同样条件下得到 228 配对、228 调用，并在模型中核验 2,000,000 人迁移。另验证无法写入州接收标记时不调用引擎，以及国内目的州在没有 POP 标记时不能转出本批新移民。上述模型对照验证了脚本可以绕过该类变量问题。实机筛选失败的具体表达式仍需以游戏 error.log 或 RC3 实测确定。

1.0.0 的上下界误用和旧模型的同类误读已经确认。1.0.1 修完上下界后，反馈仍然失败。在 1.0.2 确定能从代码确认的缺陷是“把未验证即时州差值当成失败并允许再次发起”。该路径既可能发生在请求零移动时，也可能发生在移动已执行但统计尚未更新时。反馈没有附该版本的原生日志或分阶段读数，无法确定最初停在哪一环。新版的旧日志字段不兼容是另一个可确认的问题，与 1.13.11 的原始报告分开处理。

执行链为 Journal → Button（玩家/中国资格与全局冷却/锁）→ 锁定 → Country POP 快照 → 每个 State Region 的实际州 → 文化×地区额度并在州间均分 → POP 内原生效果 → 通过保存的两个州重新求同文化合计 → 核对守恒且不超过请求 → 完成结算，或停止挂牌待确认。源对象被消耗后，正式脚本不读取其迁出后的大小。本国来源与接收标记在操作结束清除。外州相关临时标记在一天后到期。已有成功/冷却/历史变量保留。

最优先的待验证假设是跨国移动的参数绑定和单位、同调用链的统计/对象刷新。独立探针在一次测试周期内覆盖常数、动态值、比例、全 POP 四种请求，以及两端合计/缓存/原对象的即时与翌日读数。翌日正常人口变动可能混入结果，不能用于正式自动结账。原生操作没有已知返回值或回滚，无法确认的操作锁只随回档解除。端到端目标尚未验证。

迁移开始时标记本国来源 POP，地图遍历收窄为 30 个设计地理域。每个文化和目的州的有效份额以原生 Country POP 枚举筛选来源。每次实际调用另扫两州各两次，换取相互独立的核验读数。若有 P 个本国 POP、D 个目的实际州、K 次调用，由于文化数固定，配对扫描量级为 O(P·D)，核验成本取决于每笔涉及的两州 POP 数。没有轮询或无界重试。未测得实际游戏耗时。
